# B2B Layer Implementation Plan

## 1. Goal

Add a B2B layer to the existing Payload CMS + Next.js B2C store:

- Separate business login portal and dashboard.
- B2B pricing per product/variant, plus a per-partner discount.
- Business partners can order at B2B prices.
- No external payment gateway for B2B; orders are paid internally by invoice / bank transfer and settled by an admin.
- B2C storefront and Stripe checkout remain unchanged.

## 2. Confirmed Decisions

| Decision | Choice |
|---|---|
| B2B identity | Shared `users` auth collection, separate `/business` portal and role-gated routes |
| Company structure | One login per partner company; company data lives on the user record |
| Partner onboarding | Public application form + admin approval |
| B2B pricing | `b2bPriceInEUR` on product/variant + optional company discount |
| Internal payment | Invoice / bank transfer, admin records settlement |
| B2C payments | Existing Stripe adapter remains B2C-only |

### Why shared `users`

`@payloadcms/plugin-ecommerce` is configured with `customers: { slug: 'users' }`. Its carts, orders, addresses and transactions relate to that single customer collection. A separate `businessUsers` auth collection would require re-implementing the entire B2B cart/order stack. Shared users keeps the plugin infrastructure, admin order management and inventory logic.

The portal is still separate at the UX, routing and access-control levels.

## 3. Current B2C Architecture (facts from the codebase)

- Payload 3.88 + MongoDB, config at `src/payload.config.ts`.
- Ecommerce collections are generated by `@payloadcms/plugin-ecommerce` in `src/plugins/index.ts`.
- Single auth collection `users`; admin access is `checkRole(['admin'])`.
- Prices live on products/variants as `priceInEUR` (integer cents).
- Cart subtotal is computed by the plugin's `beforeChange` from `priceInEUR`.
- Checkout uses Stripe Elements and the Stripe payment adapter.
- Storefront routes are localized through `src/proxy.ts` (`/foo` → `/de/foo`, `/en/foo` stays).
- Existing B2C account routes: `/[locale]/account`, `/[locale]/orders`, `/[locale]/checkout`.
- `Users.cart` is a join field; the client `EcommerceProvider` loads `user.cart.docs[0]`.
- `ProductDescription`, `AddToCart`, `VariantSelector`, `Price` are the B2C pricing/cart UI.

## 4. Target Architecture

```
/business/apply ──► business-applications (pending)
                           │ admin approves
                           ▼
                    users.accountType = b2b
                    users.b2b.status = approved
                    password-reset email
                           │
                           ▼
/business/login ──► /business/dashboard
                           │
        ┌──────────────────┼──────────────────┐
        ▼                  ▼                  ▼
   B2B catalog         B2B cart          B2B orders
   b2bPriceInEUR       channel=b2b       invoice group
        │                  │                  │
        └──────────► /business/checkout ◄─────┘
                           │
                  invoice payment adapter
                           │
                  order b2bStatus=awaiting_payment
                           │ admin marks invoice paid
                           ▼
                  b2bStatus=paid → processing → shipped → completed
```

### Key invariants

1. B2B prices are **net** (excl. VAT). VAT is added on the invoice.
2. All prices are integer cents.
3. The server always recalculates cart/order totals from current product data and the partner discount. Client-submitted prices are never trusted.
4. `accountType === 'b2b'` and `b2b.status === 'approved'` are required for every B2B route, field read, cart operation and payment call.
5. B2B orders never touch Stripe. B2C/guest orders never touch the invoice adapter.
6. Existing B2C behavior is the default when `channel`/`accountType` is missing.

## 6. Access & Roles

Add `src/access/b2b.ts`:

```ts
export const isApprovedB2B = ({ req }: AccessArgs) =>
  req.user?.accountType === 'b2b' && req.user?.b2b?.status === 'approved'

export const adminOrApprovedB2BFieldAccess: FieldAccess = ({ req }) =>
  checkRole(['admin'], req.user) || isApprovedB2B({ req })
```

Rules:

- B2B routes: server layout checks `payload.auth({ headers })`, then requires approved B2B; otherwise redirect to `/business/login`.
- B2B data: orders/carts/addresses remain owner-scoped by the plugin's `isDocumentOwner`.
- B2B price fields: hidden from anonymous/B2C REST reads via field-level access.
- B2B application data: admin-only.
- B2B settings: admin-only.
- Stripe adapter: wrap `initiatePayment` and `confirmOrder` to reject `req.user?.accountType === 'b2b'`.
- Invoice adapter: reject guests and non-B2B users; additionally re-check `b2b.status === 'approved'` on every call so a suspended account cannot order with an existing session.
- `Users.access.admin`: unchanged (`admin` role only), so B2B users cannot enter Payload admin.
- Server hooks that write admin-only fields (`b2b.status`, `b2b.discountPercent`, invoice settlement, transactions) must use Local API `overrideAccess: true`; client-facing REST calls must never be able to write them.

## 7. Authentication & Onboarding

### 7.1 Application

- Public page `/[locale]/business/apply`.
- Form posts to `/api/business-applications` with company/contact/VAT/address/terms fields.
- Show a generic success message ("We will review your application").
- Add a link to `/business/login` and `/business/apply` in the footer or business login page. Do not change the main B2C navigation except for a discreet footer link.

### 7.2 Approval

`src/collections/BusinessApplications/hooks/approveApplication.ts`:

1. Run when `status` changes to `approved` and `user` is empty.
2. Find an existing user by email.
3. If the user exists:
   - If the user is an admin, stop and require manual review.
   - Update `accountType = 'b2b'`, `b2b.status = 'approved'`, company fields, `roles = ['customer', 'b2b']`, `b2b.preferredLocale`.
4. If no user exists:
   - Generate a random password.
   - Create `users` with `accountType = 'b2b'`, `b2b.status = 'approved'`, company fields, `roles = ['customer', 'b2b']`.
5. Link `application.user` to the user.
6. Send a business password-reset email (see §7.4).
7. If `status = rejected`, optionally send a rejection email.

### 7.3 Business login

- Page `/[locale]/business/login`.
- `BusinessLoginForm` posts directly to `/api/users/login`:

```json
{ "email": "...", "password": "...", "portal": "business" }
```

  - Clear `localStorage.cart` and `localStorage.cart_secret` (prevents a guest B2C cart leaking into the B2B portal).
  - Hard navigate to `/${locale}/business/dashboard`.

### 7.4 Password reset / forgot password

- Payload's default reset email links to `/admin/reset/{token}`, which B2B users cannot access.
- Add `src/b2b/utilities/sendBusinessPasswordReset.ts`:
  - Call `payload.forgotPassword({ collection: 'users', data: { email }, disableEmail: true })`.
  - Build a link to `/${locale}/business/reset-password?token=${token}`.
  - Send it with `payload.sendEmail`.
- Add a custom endpoint `src/app/(app)/api/business/forgot-password/route.ts`:
  - Find the user by email.
  - Only send if the user is an approved B2B account.
  - Always return a generic success response to avoid account enumeration.
- Add `/[locale]/business/forgot-password` and `/[locale]/business/reset-password` pages.
- The reset page posts to the standard `/api/users/reset-password`; on success the auth cookie is set and the user is redirected to `/business/dashboard`.

### 7.5 Business logout

- Add `/[locale]/business/logout` or a client `BusinessLogoutButton`.
- POST `/api/users/logout`, clear local cart storage, then navigate to `/business/login`.

### 7.6 Session caveat

Payload uses a single cookie (`payload-token`) whose JWT encodes the collection. A user cannot be logged into B2C and B2B at the same time. Logging into the business portal replaces the B2C session. This is acceptable for separate portals; document it in the login page copy.

## 8. B2B Pricing

### 8.1 Resolution

`src/b2b/utilities/pricing.ts`:

```ts
resolveB2BUnitPrice({ product, variant, discountPercent }) {
  const base = variant?.b2bPriceInEUR ?? product?.b2bPriceInEUR
  if (base == null) throw new Error('PRODUCT_NOT_B2B_ELIGIBLE')
  const discount = Math.min(Math.max(discountPercent ?? 0, 0), 100)
  return Math.round((base * (100 - discount)) / 100)
}
```

- `base` is net cents.
- Discount applies to the B2B price only.
- No retail fallback.
- Variant price overrides product price.
- Minimum order quantity comes from `variant.b2bMinOrderQuantity ?? product.b2bMinOrderQuantity ?? 1`.

### 8.2 Totals

```ts
calculateB2BTotals(netSubtotal, vatRatePercent) {
  const vatAmount = Math.round((netSubtotal * vatRatePercent) / 100)
  return { netAmount: netSubtotal, vatAmount, grossAmount: netSubtotal + vatAmount }
}
```

`cart.subtotal` = net. `transaction.amount` and `order.amount` = gross. `order.invoice.netAmount/vatAmount/grossAmount` keep the breakdown.

### 8.3 Display

- B2B catalog and product pages show net prices and "excl. VAT" / "zzgl. MwSt.".
- Do not show the retail price to B2B users.
- Show the partner discount and the minimum order quantity where relevant.
- Add `src/components/business/B2BPrice.tsx` or extend `Price` with a `suffix` prop.
- B2C product pages remain unchanged.

## 9. B2B Cart

### 9.1 Server-side channel and pricing

Replace the plugin's cart `beforeChange` with `src/b2b/hooks/setB2BCartPricing.ts`:

1. Determine the user:
   - `isApprovedB2B(req.user)` → `channel = 'b2b'`.
   - otherwise → `channel = 'b2c'`.
2. On create, force `customer = req.user.id` for authenticated users. Generate the guest secret exactly like the plugin for anonymous carts.
3. For each item:
   - Load product/variant with Local API `overrideAccess: true`, selecting B2B price, retail price, inventory, and min quantity.
   - B2B:
     - If eligible and `quantity >= minOrderQuantity`: `unitPrice = resolveB2BUnitPrice(...)`, `b2bIssue = null`.
     - If not eligible or below minimum: set `unitPrice = 0`, `lineTotal = 0`, and `b2bIssue` to a message. Do **not** throw during cart mutations, otherwise a stale/ineligible item could block its own removal. The checkout adapter is the authoritative rejection point.
   - B2C:
     - `unitPrice = variant?.priceInEUR ?? product.priceInEUR` (existing behavior).
     - `b2bIssue = null`.
   - Set `item.unitPrice` and `item.lineTotal = unitPrice * quantity`.
4. Set `data.subtotal` from the sum of line totals.
5. Do not trust client-provided `unitPrice`, `lineTotal`, `b2bIssue`, `channel`, or `subtotal`.

Keep the plugin's secret generation and `afterRead` behavior. Do not append the default `beforeChangeCart` after the custom hook; replace it to avoid the subtotal being overwritten with retail prices.

### 9.2 Cart UI

- `/[locale]/business/cart` uses `useCart()` state but performs mutations through explicit fetches to `/api/carts/:id/update-item` and `/api/carts/:id/remove-item` so errors can be shown. Call `refreshCart()` after each mutation.
- Display unit price (net), quantity, line total, net subtotal, VAT, and gross total.
- Show `b2bIssue` as an inline warning and keep the Remove control enabled for that line.
- Add a quantity input honoring `b2bMinOrderQuantity`.
- Do not reuse the B2C cart modal for B2B. On business paths, the global Navbar should show a link to `/business/cart` instead of the B2C cart drawer (see §11.7).

### 9.3 Guest cart handling

- Clear `localStorage.cart` and `localStorage.cart_secret` on successful B2B login.
- If a guest cart is nevertheless loaded, the cart hook forces `channel = 'b2b'` and recalculates prices on the first update.

### 10.1 Invoice payment adapter

```ts
{
  name: 'invoice',

  group: { name: 'invoice', type: 'group', ... }, // transaction fields

  confirmOrder,
}
```

Client counterpart `src/b2b/payments/invoiceAdapterClient.ts`:

```ts
{ name: 'invoice', label: 'Invoice', initiatePayment: true, confirmOrder: true }
```

Register both in `src/plugins/index.ts` and add the client adapter to `src/providers/index.tsx` `paymentMethods`.

### 10.2 `initiatePayment`

Inputs: `req`, `data.cart`, `data.billingAddress`, `data.shippingAddress`, `transactionsSlug`.

1. Guard: `req.user` must be an approved B2B user. Otherwise throw.
2. Load the cart fresh with `depth: 2`, `overrideAccess: true`; verify `cart.customer === req.user.id`, require `cart.channel === 'b2b'`, and require non-empty items.
3. Recompute every line with current prices and the partner discount (do not trust `cart.subtotal`). Update the cart items/subtotal with Local API `overrideAccess: true`.
4. Validate inventory, B2B eligibility, min quantity, and optional `minimumOrderValue` (compare against the net subtotal). Reject if any cart item has `b2bIssue`.
5. Load `b2b-settings` (`overrideAccess: true`).
6. Allocate an invoice number (see §10.5), compute due date, net/VAT/gross, and snapshot bank details.
7. Create a transaction:

```ts
{
  customer: req.user.id,
  customerEmail: req.user.b2b.invoiceEmail || req.user.email,
  amount: grossAmount,
  currency: 'EUR',
  items: flattenedItems, // product, variant, quantity, unitPrice, lineTotal
  paymentMethod: 'invoice',
  status: 'pending',
  cart: cart.id,
  billingAddress,
  shippingAddress,
  invoice: { invoiceNumber, dueDate, netAmount, vatAmount, vatRate, grossAmount, bank... }
}
```

8. Return `{ message, transactionID, invoiceNumber, dueDate, netAmount, vatAmount, grossAmount }`.

**Error surfacing:** the plugin's `initiatePayment` endpoint converts adapter exceptions into a generic 500. Return expected business validation failures (minimum order value, out-of-stock, ineligible item) as `{ message, error: '...' }` in the adapter response instead of throwing; the client's `initiatePayment` checks `responseData.error` and throws that message. Throw only for unexpected/infrastructure errors.

### 10.3 `confirmOrder`

1. Guard: approved B2B user.
2. Load the transaction by `transactionID`; verify `customer === req.user.id`, `paymentMethod === 'invoice'`, `status === 'pending'`.
3. Create the order:

```ts
{
  customer: req.user.id,
  customerEmail: invoiceEmail,
  items: transaction.items, // includes product_name snapshot after order hook
  amount: transaction.amount,
  currency: 'EUR',
  status: 'processing',
  channel: 'b2b',
  b2bStatus: 'awaiting_payment',
  billingAddress,
  shippingAddress,
  transactions: [transaction.id],
  companySnapshot: { companyName, vatId, contactName, email, phone },
  purchaseOrderNumber,
  customerNotes,
  invoice: { ...transaction.invoice, paymentReference: invoiceNumber }
}
```

4. Mark the cart purchased and clear its items so the active-cart join no longer returns it.
5. Update the transaction with `order: order.id`.
6. Send the order-confirmation email to the partner and the new-order notification to `b2b-settings.orderNotificationEmail`.
7. Return `{ message, orderID, transactionID }`.

The plugin's `confirmOrderHandler` then decrements inventory from the transaction items. This is intentional reservation semantics: stock is reserved when the invoice order is placed.

### 10.5 Invoice numbering

`src/b2b/utilities/invoiceNumber.ts`:

- Use the `counters` collection with an atomic Mongo `findOneAndUpdate`:

```ts
const counter = await payload.db.connection
  .collection('counters')
  .findOneAndUpdate(
    { key: `invoice-${year}` },
    { $inc: { value: 1 } },
    { upsert: true, returnDocument: 'after' },
  )
```

- Format: `${prefix}-${year}-${String(value).padStart(5, '0')}`.
- Add a unique index on `counters.key`.
- On `orders.invoice.invoiceNumber`, use a normal Payload `index: true` (not `unique: true`), because B2C orders have no invoice number and a plain unique index would collide on multiple missing values. Optionally add a Mongo partial unique index:

```js
db.orders.createIndex(
  { 'invoice.invoiceNumber': 1 },
  { unique: true, partialFilterExpression: { 'invoice.invoiceNumber': { $type: 'string' } } },
)
```

- If the adapter's raw Mongo access is unavailable in a given environment, fall back to a dedicated `invoice-sequences` collection updated through the Mongo adapter with `$inc` and a unique `key`.
- A failed `confirmOrder` after `initiatePayment` may leave a numbering gap; document as acceptable.

### 10.6 Admin settlement

Admin workflow:

1. Open the B2B order in Payload.
2. Enter `invoice.paidAt` and `invoice.paymentReference` / `invoice.settlementNotes`.
3. Save.
4. `beforeChange` sets `b2bStatus = 'paid'`.
5. `afterChange` sets the linked transaction to `succeeded`, sets `invoice.paidBy`, and sends the payment-received email.
6. Admin then moves `b2bStatus` through `processing` → `shipped` → `completed` as fulfillment progresses.

For convenience, add `b2bStatus` and `invoice.invoiceNumber` to the orders admin `defaultColumns`.

### 10.7 Cancellation & restock

- When an admin sets `b2bStatus = 'cancelled'` (or plugin `status = 'cancelled'`), the order hook:
  - Sets `inventoryRestored = true`.
  - Increments inventory for each item once.
  - Marks the transaction `cancelled` if still pending.
  - Sends a cancellation email.
- Guard with `inventoryRestored` so repeated saves cannot double-restock.

## 16. Risks & Edge Cases

| Risk | Mitigation |
|---|---|
| Shared auth cookie means B2C and B2B sessions cannot coexist | Documented; separate portals; logging into one replaces the other |
| Plugin cart `beforeChange` overwrites subtotal with retail price | Replace, do not append, the cart `beforeChange` hook |
| Client sends a forged price/channel | Server sets `channel`, `unitPrice`, `lineTotal`, `subtotal`; client field access is false |
| B2B price exposed publicly | Field-level read access checks `accountType`/`b2b.status` |
| B2B user calls Stripe endpoints | Wrap the Stripe adapter's `initiatePayment`/`confirmOrder` with a B2B rejection |
| B2C/guest calls the invoice adapter | Guard every adapter call and return 403 |
| Suspended account with an existing JWT | Re-check `b2b.status` in the adapter and route layout, not only at login |
| Inventory reserved before payment | Intentional; cancellation hook restocks once via `inventoryRestored` |
| Invoice number duplicates under concurrency | Atomic `counters` `findOneAndUpdate` with unique index |
| VAT rounding differences | Integer cents; round VAT once at the totals level; keep net/VAT/gross snapshots |
| First approved B2B user becomes admin on a fresh deployment | Skip `ensureFirstUserIsAdmin` for `accountType === 'b2b'` |
| Guest B2C cart leaks into B2B portal | Clear local cart storage on B2B login; server forces channel on update |
| Provider loads a purchased cart | Filter `Users.cart` join by `purchasedAt: { exists: false }`; clear items after purchase |
| Address `customer` not auto-assigned | Pass `isCustomer` in the plugin access config (`req.user && !admin`) |
| Existing B2C customer converted to B2B loses B2C login | Document; admin review; optionally preserve read-only B2C order history later |
| Localization gaps | Use a de/en dictionary for all new pages and emails; default `de` |

## 19. Bugfix: Approving a Business Application Fails

### Symptom

- Saving an application as `pending` or `rejected` works.
- Saving it as `approved` returns an error in the admin UI; the terminal likely shows a MongoDB transaction/write-conflict error or a nested-transaction error.

### Root cause (from code inspection)

`src/collections/BusinessApplications/hooks/approveApplication.ts` is an `afterChange` hook that performs database writes:

- `payload.create` / `payload.update` for the `users` document.
- `payload.update` for the **same** `business-applications` document (to set `user`).
- `payload.forgotPassword`, which updates the user's reset token.

None of those calls pass the hook's `req`. Each local API call therefore starts its own transaction while the outer application update is still open. Updating the same application document from its own `afterChange` is the direct conflict. Pending/rejected do not enter this branch, which matches the symptom.

There is a second bug in the same path: because `payload.create` is called without `req`, `guardB2BUserCreate` sees no admin user and forces the new user to `b2b.status = 'pending'` and `roles = ['customer']`. Even if the save succeeds, the approved partner is actually pending.

### Fix plan

1. Change the collection hook from `afterChange` to `beforeChange`:

```ts
hooks: {
  afterChange: [sendApprovalEmail],
  beforeChange: [approveApplication],
}
```

2. Rewrite `approveApplication` as a `CollectionBeforeChangeHook`:

- Trigger only when:
  - `operation === 'update'`
  - `data.status === 'approved'`
  - `originalDoc?.status !== 'approved'`
  - no `data.user` and no `originalDoc?.user`
- Initialize a request-scoped map:
  ```ts
  if (!req.context) req.context = {}
  const approvals = (req.context.b2bApproval ||= {})
  ```
- Find an existing user by email with `req`:
  ```ts
  await payload.find({ ..., req })
  ```
- Create or update the user with `req`:
  ```ts
  await payload.create({ ..., req, overrideAccess: true })
  await payload.update({ ..., req, overrideAccess: true })
  ```
- Set `req.context.b2bApproval = true` just before `payload.create` so `guardB2BUserCreate` does not downgrade the account. Clear it after.
- Do **not** call `payload.update` on the application. Instead set the link on the incoming data:
  ```ts
  data.user = userID
  ```
- Set the reset token inside the same transaction:
  ```ts
  const token = await payload.forgotPassword({
    collection: 'users',
    data: { email },
    disableEmail: true,
    overrideAccess: true,
    req,
  })
  approvals[String(application.id)] = { email, token, locale: 'de' }
  ```
- Return the modified `data`.

3. Add `sendApprovalEmail` as a small `CollectionAfterChangeHook`:

- Runs only when the application transitions to approved.
- Reads `req.context?.b2bApproval?.[String(doc.id)]`.
- Sends the reset email with the stored token; performs no DB writes.
- Catches and logs email failures; never fails the approval.

4. Update `guardB2BUserCreate`:

```ts
if (req.context?.b2bApproval === true) return data
```

Place this before the pending/roles override. This makes the approval flow safe even when it is triggered by a script with `overrideAccess: true` and no admin `req.user`.

5. Refactor `src/b2b/emails/sendBusinessPasswordReset.ts` into two helpers:

- `requestBusinessPasswordResetToken({ payload, email, req? })` — calls `forgotPassword` with `disableEmail: true` and the optional `req`.
- `sendBusinessPasswordResetEmail({ payload, email, token, locale })` — sends only the email.

Update the custom `/api/business/forgot-password` endpoint to call both helpers. It has no outer transaction, so it can omit `req`.

6. Add an integration test in `tests/int/b2b/approval.int.spec.ts`:

- Create an application as admin.
- Update it to `approved` through the Local API with the admin `req`.
- Assert:
  - application `user` is set
  - user `accountType === 'b2b'`
  - user `b2b.status === 'approved'`
  - roles include `customer` and `b2b`
  - `resetPasswordToken` is set
  - no error is thrown
- Repeat with an existing B2C user's email and assert the user is converted, not duplicated.

7. Manual validation:

- Approve a new application in the admin UI.
- Confirm the terminal no longer shows a transaction/write-conflict error.
- Confirm the reset email arrives and the partner can set a password.
- Confirm `/business/login` accepts the partner and `/business/dashboard` loads.

### If the terminal error is different

- Duplicate-key error on `users.email`: check the existing-user lookup for case/whitespace and normalize both sides.
- `Missing email`: check `application.email` before calling `forgotPassword`.
- Resend/email adapter error: verify `RESEND_API_KEY`, `EMAIL_FROM_ADDRESS`, `EMAIL_FROM_NAME`; email failures are already caught in the helper, but `forgotPassword` must be called with `disableEmail: true` and the refactored token helper.

The `beforeChange` + `req` fix is still correct for those cases because it removes the nested transaction and the second write to the application document.
